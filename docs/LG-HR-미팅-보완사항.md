## 결론부터

**"편성 화면 하나만 제대로 만들어라"** 가 이 회의의 전부입니다.

책임님이 마지막에 못 박으셨습니다.

> "채팅이나 팀 협업 이런 거 고려하지 마시고 이거만 하나씩 하시죠."
> "핵심은 저 결과가 잘 나와서 오퍼레이션 할 수 있게, 편성까지가 잘 나오면 좋겠어요."

우리가 넓게 벌려놓은 이해관계자 4개 화면보다, **스케줄 편성 화면의 자유도와 수정 UX**가 이번 평가의 기준입니다.

---

## P0 — 반드시 고쳐야 할 것

### 1. 편성 드래그 수정 전면 개방

지금 하드 제약 때문에 못 움직이는 것이 가장 큰 문제입니다.

- 빈 슬롯 이동뿐 아니라 **이미 배정된 사람끼리의 스왑**도 가능해야 함
- 제약 위반도 **토글로 해제** 가능해야 함

> "결국 이렇게 해줘도 자기가 하고 싶은 대로 할 거거든요. 그런 자유도를 많이 줘야 될 것 같아요."

### 2. 수정 시 재계산(솔버) 돌리지 않기

1차 결과는 빠르게 뽑고, 이후에는 손으로 고치고 바로 저장되는 흐름으로 갑니다.

- 우리가 공들인 **솔버 최적화는 사실상 요구사항이 아님**
- 단, 학사 사이에 석사가 끼거나 타 팀이 섞이는 것은 안 되므로 **기본 룰은 유지하되 위반 시 경고 수준**으로 처리

> "최적은 없거든요. … 최적보다 사용성이 더 중요한 것 같아요."

### 3. 팀 단위 연속 배치 옵션

1일차 전무기술팀처럼 오전 8시 / 오후 1시로 쪼개지면 안 됩니다. 면접관이 하루에 두 번 나와야 하기 때문입니다.

- 가로(연속) 배열 옵션 추가
- 빈 슬롯 최소화 옵션 추가

### 4. 단계적 확정 / 통보 기능 복구

POC에는 있었으나 이번 제품화 때 시간이 없어 빠진 부분입니다.

- **1일차 확정 → 픽스 → 2일차 재배치 시 영향 범위 축소 → 3일차** 로 내려가는 구조
- 책임님이 가장 관심을 보인 **"고쳐도 전체가 안 깨지게"** 하는 핵심 장치
- 재배치 리스크를 단계별로 줄여주는 논리이므로 우선순위 높게 반영

### 5. 워딩 정리

> "워딩만 조금 AI스럽지 않게 바꿔주세요."

"변경 / 대응 / 재통보 / 전형 종료의 산출물" 같은 표현을 전부 실무 용어로 교체합니다. 직접적인 요청이었습니다.

## 새로 넣어야 할 기능

### 이력서 PDF 뷰어 (모달)

지원자 리스트에서 클릭하면 어디서든 바로 뜨게 합니다.

- 면접위원에게 필요한 3종: **일정 / 화상 면접 링크 / 이력서 PDF**
- 화상 링크 관리 기능도 함께 구현
- PDF 저장 위치와 호출 방식은 HR 쪽도 미정이므로 **우리가 파일명 규칙안을 먼저 제안**

> "그걸 HR에서는 어떻게 할 거냐, 어디에 저장을 해놔야 그거를 불러와가지고 할 거냐 이런 고민들이에요."

### 프로젝트(전형) 단위 관리

신입 1차 / 2차, 국내 / 해외 / 수시를 각각 별도 프로젝트로 분리합니다.

- 전형마다 데이터·DB 구조·알고리즘이 다름
- 한 명이 프로젝트를 만들어 다른 간사에게 배포하거나, 조인해서 함께 쓰는 구조

### 전형 생성 시 상세 세팅 확대

현재는 기간·일일 슬롯만 있습니다. 다음 항목이 추가로 필요합니다.

- **면접 시간 / 휴식 시간 / 시작 시각**
- HR은 조직명도 수시로 바뀌는 등 변동성이 커서 **옵션을 최대한 열어주는 쪽**을 원함
- 반대로 면접관 쪽 입력은 최소화가 맞음
- 우리가 "허들이라서 뺐다"고 한 것은 판단 미스 → **기본값 노출 + '상세 설정' 접기** 형태로 복구
- 반복 사용 이력이 쌓이면 템플릿으로 불러오는 것까지 장기 과제

> "HR은 최대한 많이 범위를 열어줘야 튜닝도 할 수 있고 … 면접관은 최소화하는 게 좋아요."

### 취합 엑셀 포맷 흔들림 대응

팀마다 열을 지우고 추가해서 올리기 때문에 입력 포맷이 제각각입니다. (HR 자체 포맷은 거의 고정)

- 팀명 오타(`AI솔루션팀` → `AI솔루션T`) 케이스는 **우리가 고려하지 못했던 부분**
- 팀명 목록 대조 + LLM 분류로 1차 필터링, 최종 판단은 사람이 확인하는 구조

### 변경 이력 및 알림

현재는 메일로 V1~V4가 오가고 간사는 V4만 확인합니다.

- 누가 언제 무엇을 바꿨는지 **로그** 기록
- 최신 변경을 간사가 놓치지 않도록 **알림** 제공

> "팀이 많으니까 그거에 대한 조절, 분배가 중요합니다."

## 챙겨야 할 것 (우선순위는 낮음)

### KPI 항목 확보

운영 대시보드 KPI를 지금은 우리가 임의로 채워놓은 상태입니다.

> "채용 기간 동안에 봐야 할 KPI들이 아마 더 있을 것 같아요."

라고 열어두고 실제로 무엇을 보시는지는 확인하지 못했습니다. 당장의 구현 이슈는 아니지만 **다음 미팅 질문 리스트에 넣어 반드시 받아옵니다.**

### 클릭 depth 축소

튜토리얼 영상 자체는 칭찬받았지만, 곧바로 클릭 수 지적이 이어졌습니다.

> "그거 되게 잘 만드셨더라고요. 근데 너무 많이 눌러야 돼서 … 되게 처음엔 예뻤는데 이게 힘들겠다."

지금 당장 손댈 우선순위는 아닙니다. 다만 **앞으로 기능을 추가할 때마다 이 피드백을 기준선으로 삼아** 클릭 단계가 늘어나지 않도록 관리합니다.

> "그거에는 아까 제가 말씀드린 뭐 저런 채팅이나 팀과의 협업 혹은 이런 거 고려하지 마시고 이거만 하나씩 하시죠."

## 동시 사용 설계 (추후 진행)

> 이번 라운드에서는 **구현하지 않습니다.** 책임님이 협업 기능을 명시적으로 제외하셨으므로 P0에 집중하고, 아래는 착수 시점을 위한 설계 기록입니다.

### 전제 — 조인 기준으로 설계한다

책임님이 두 가지를 나란히 말씀하셨습니다.

> "제가 프로젝트를 만들어서 다른 간사에 **배포**를 한다던지, 누군가 한 명이 프로젝트를 만들고 그걸 **조인**해서 쓰면 좋겠죠."

이 둘은 성격이 완전히 다릅니다.

- **배포** — 설정만 복사해 각자 별개 전형으로 운영 → 동시성 문제 없음
- **조인** — 같은 전형 하나에 여러 간사가 참여 → 동시성 문제 발생

이어서 *"HR 간사가 여러 사람들 조인해서 한 프로젝트에서 같이 보고"* 라고 하신 것으로 보아 조인 쪽에 무게가 있습니다. **더 어려운 쪽인 조인을 기본 가정으로 잡습니다.** 배포로 판명나면 기능을 켜지 않으면 그만이지만, 반대는 데이터 모델을 다시 손봐야 합니다.

### 편성 캔버스는 간사 전용 화면이다

책임님이 화면을 이렇게 나누셨습니다.

> "HR 간사 페이지는 그들끼리 볼 수 있는 하나가 있을 거고 / HR 간사랑 팀 담당자랑 조인해서 관리되는 그 페이지가 또 있을 것 같고"

그리고 관계자에게 주는 것의 성격을 이렇게 규정하셨습니다.

> "어떻게 보면 **정보를 열어주는** 거죠. H팀 따로, HR 따로. 면접위원한테는 링크를 보내준다거나 면접 일정을 보내준다거나 그런 인폼을 하는 역할이 되겠죠."

열어주는 것은 **정보**이지 **편집권**이 아닙니다. 면접위원에게 필요한 것도 *"언제 하는지, 화상 링크, 이력서 PDF 그 세 개"* 뿐입니다. 따라서 동시편집 문제는 **간사 ↔ 간사** 한 축으로 좁혀집니다.

### 잠금 단위는 일차(Day)

새 개념을 만들지 않고, 이미 설계한 **단계적 확정(P0 · 04)** 의 경계를 그대로 씁니다.

| 근거 | 내용 |
|---|---|
| 확정 단위가 이미 일차 | 잠금과 확정이 같은 경계를 쓰면 사용자가 개념을 하나만 배웁니다 |
| 하드 제약이 일차 안에서만 걸림 | 면접관 중복 배정 제약은 일차를 넘지 않으므로 일차끼리 간섭하지 않습니다 |
| 재배치 영향 범위도 일차 안 | 1일차를 고쳐도 2일차가 깨지지 않습니다 |

```
전형: 2026 신입 1차 (3일)

  1일차  [확정됨]           총괄만 해제 가능
  2일차  [편집중 · 김간사]   다른 간사는 실시간 읽기 전용
  3일차  [대기]             아무나 잡을 수 있음
```

**대안을 배제한 이유**

| 안 | 배제 사유 |
|---|---|
| 완전 동시편집 | 드래그 중 남이 같은 칸을 채우면 제약이 깨집니다. *"자유도를 많이 줘야"* 와 실시간 검증이 정면충돌합니다 |
| 방(면접실) 단위 분할 | 경계를 넘는 이동이 막힙니다. 책임님이 가장 많이 할 거라던 *"삭제하고 이동하고 하는 업무"* 를 죽입니다 |
| 전형 전체를 한 명이 독점 | 3일치를 한 명이 다 짤 동안 나머지가 대기합니다. 조인의 의미가 사라집니다 |

### 1단계 — 편집권 배턴

- 간사가 일차를 열면 그 일차의 편집권을 잡습니다. 다른 간사는 같은 화면을 실시간으로 보되 읽기 전용이며, 상단에 "김간사님이 편집 중"이 표시됩니다
- 다른 간사는 **다른 일차를 동시에 편집**할 수 있습니다. 실제로 동시에 일할 여지는 여기서 나옵니다
- 유휴 5분이면 편집권 자동 해제, 총괄 간사는 언제든 강제 회수 — *"HR 권한이 제일 쎄요"*
- 확정된 일차는 잠기고, 해제 시 사유가 로그에 남습니다

### 2단계 — 미확인 변경 알림 배지

책임님이 지적한 진짜 고통은 충돌이 아니라 **인지**였습니다.

> "지금은 버전 1, 2, 3, 4가 다 메일로 오고 HR 간사는 V4만 보거든요. 맨 마지막 최신 업데이트만 보고. 여기서 관리가 되면 그 최신 업데이트 내용들을 간사가 인지를 잘 해야 할 수 있는 시스템인가요?"
> "로그가 남는다거나 업데이트 했습니다 라고 안다거나. 팀이 많으니까 그거에 대한 조절, 분배가 중요합니다."

- **단일 최신본**이 항상 화면에 있으므로 V1~V4가 애초에 생기지 않습니다
- 편성 화면 상단에 **"내가 마지막으로 본 이후 변경 N건"** 배지. 누르면 `김간사 · 14:32 · 홍길동 2일차 3방 → 2방` 형태의 델타 목록이 뜨고, 확인하면 배지가 지워집니다
- 일차 확정 시마다 **스냅샷 자동 저장** — 실무의 V1/V2/V3 개념을 되돌리기 가능한 형태로 흡수합니다

**로그와 알림은 서로 다른 층입니다.**

| 구분 | 역할 | 소속 |
|---|---|---|
| 로그 | 모든 변경을 빠짐없이 적재 (누가 / 언제 / 누구를 / 어디서 어디로). 감사 · 되돌리기용 | 데이터 모델 |
| 알림 배지 | 로그를 "내가 마지막으로 본 시점" 기준으로 걸러 보여줌 | 화면 기능 |

로그만 있으면 아무도 읽지 않아 지금의 메일 상황과 동일해집니다. 알림이 로그를 **읽게 만드는** 장치입니다.

### 팀 담당자 · 면접위원은 요청 큐로 붙인다

이쪽은 동시편집이 아니라 요청 처리입니다.

> "1차적으로 맞춰야 되고 안 되면 대차민원을 보내요. 아니면 안 된다고 메일을 쓰거나. 저 10시 안 됩니다, 바꿔주세요."
> "그럼 그분들이 안 된다는 메시지를 보낼 때도 이 안에서 되는 게 훨씬 낫겠네요?" → "그럼 좋죠. 지금 메일로 모든 걸 소통하니까."

- 면접위원이 자기 일정 화면에서 "10시 불가"를 누르면 편성 화면의 해당 카드에 경고가 표시됩니다
- 간사가 카드를 눌러 승인하면 이동 후보 슬롯이 뜨고, 옮기면 요청이 닫힙니다
- 팀 담당자의 지원자 추가 · 삭제 요청도 같은 큐로 수렴합니다
- 이들에게 **편집 권한은 주지 않습니다.** 요청만 올리고 반영은 간사가 합니다

### 착수 시 선행 준비

착수 시점에 가장 먼저 잡아야 할 항목입니다. 컬럼만 미리 추가해두면 이후 마이그레이션이 필요 없습니다.

- 배치 레코드에 `updated_by` · `updated_at` · `version`
- 저장 시 version 비교 → 불일치하면 "다른 사람이 방금 변경했습니다" 안내 (낙관적 동시성)
- 변경 이벤트 테이블 (누가 / 언제 / 누구를 / 어디서 어디로)
- 일차에 `상태`(대기 · 편집중 · 확정) 및 `잠금 소유자` 필드

동기화는 **3~5초 폴링으로 충분합니다.** 사내 서버 도커 배포이므로 WebSocket도 가능하지만 동시 사용자가 수 명 수준이라 오버스펙입니다.

### LG에 확인할 항목

1. 전형 하나에 간사가 **몇 명**이나 붙는가. 실제로 동시에 편성을 만지는가, 한 명이 짜고 나머지는 검토인가
2. "배포"는 설정만 복사해 각자 별도 전형으로 쓰는 것인가, 같은 전형에 같이 들어오는 것인가
3. 간사들 사이에 담당 구분이 있는가 (일차별 · 직군별 · 사업부별)
4. 인수인계 상황이 있는가 (휴가 · 교대로 중간에 담당이 바뀌는 경우)

1번 답에 따라 설계 규모가 크게 갈립니다. "실제로는 한 명이 짠다"면 위 설계의 절반은 불필요합니다.
