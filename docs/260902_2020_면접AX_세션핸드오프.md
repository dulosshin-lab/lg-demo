## 3. 위반 판정을 새로 정의했다 (핵심)

`Sched.validate()` 는 **자동 편성 결과**를 검사하려고 만들어졌다. 손으로 고친 표에 그대로 쓰면 어긋난다. **실데이터로 확인한 내용이다.**

| 규칙 | 엔진 판정 | 편집 모드 판정 (`src/lite/violations.ts`) |
|---|---|---|
| ① 학력 | 구간끼리 겹치나 (집합 대 집합) | **이 사람이 자기 학력의 기준 구간 밖인가** (사람 단위) |
| ② 중복 | — | **엔진 것을 문장까지 그대로** 쓴다 |
| ③ 연속 | 조 분산 + 세션 끊김을 따로 셈 | **덩어리 수** (`blocksOf`), 팀×날짜당 한 줄 |
| ④ 첫타임 | — | 엔진 것 그대로 |

### 왜 ①을 바꿨나 — 실측

석사 **1명**을 학사 구간으로 옮긴 결과:

```
현행 validate:  ①3건
  · 1일차 3세션에 학사·석사 혼재                    ← 유용
  · 학사 구간 안에 석사 1건이 끼어듦                 ← 중복
  · 석사 구간(전역 3~20세션) 안에 학사 37건이 끼어듦  ← 손대지 않은 37명을 범인으로 지목

편집 모드:      ①1건
  · 가바롬(석사)이 학사 구간에 있습니다 — 1일차 3세션
```

| 상황 | 현행 ① | 편집 모드 ① | 실제 손댄 수 |
|---|---|---|---|
| 편집 없음 | 0 | 0 | 0 |
| 석사 1명 이동 | 3 | **1** | 1 |
| 석사 3명 이동 | 5 | **3** | 3 |
| 위반 없는 이동 10회 | 0 | 0 | 0 |

**위반 건수 = 담당자가 예외로 둔 사람 수.**

### 경고 피로를 갈랐다

첫 화면에서 패널이 **④ 첫 타임 13건**(전부 기준선)으로 뒤덮여 방금 만든 위반이 묻혔다. `sinceBase` 로 갈랐다:

```
내가 만든 위반 3건          ← 상단 · 빨간 칩
알고 있음으로 표시한 것 1건
▸ 1차 편성부터 있던 것 16건  ← 접힘
```

손대지 않았으면 **「내가 만든 위반」은 항상 0건**이다.

### 카드 표식

| | 뜻 | 규칙 |
|---|---|---|
| **▲ 빨강** | 손봐야 함 | ② 같은 시간대 중복 |
| **● 진회색** | 내가 만든 예외 | ① 학력 구간 밖 |
| **● 연회색** | 1차 편성부터 | ④ 첫 타임 등 |

격자 위 범례 + 기호 롤오버 툴팁(`position: fixed`, 스크롤 영역에 안 잘림)으로 설명한다.

## 4. 저장 구조 — SQLite 전환을 염두에 둔 모양

지금은 localStorage 이지만 **SQLite 2테이블과 1:1** 이다. 옮길 때 `INSERT ... SELECT` 한 줄.

```
ax.v1.session   → { v, id(ULID), savedAt, roster, schedule, edit, proposals }
```

**나중에 넣으면 과거 데이터가 비므로 지금부터 지킨 것 6가지:**

1. **ULID** — 26자, 시간순 정렬. `crypto.randomUUID()`(v4)는 정렬이 안 돼 쓰지 않음
2. **actor** — 값이 자리표시자(`local`/`HR 간사`)여도 반드시 기록
3. **baseSeq** — 작성 시점에 본 마지막 seq. 서버 도입 시 충돌 감지용
4. **append-only** — 이벤트는 덧붙이기만. 취소는 반대 이벤트를 더하는 것
5. **파생값 미저장** — `result.grid` 는 저장하지 않고 `placed` 로 재구성 (저장하면 60명분이 두 벌이 되고 참조가 갈라져 **한쪽만 수정되는 버그**가 난다)
6. **평평한 필드** — `from_day`/`from_slot`, snake_case 유지

**용량 실측: 618KB** (명단 484KB = 마스터 467명 전체 + 편성표 134KB). 5MB의 12%. 편성안 약 8개가 한계이므로 **SQLite 전환 시점이 예상보다 이르다.**

> 승인으로 생긴 편집 이벤트에는 `proposalId` 가 실린다. 되돌릴 때 이 연결로 요청도 함께 철회한다(D14).

## 5. 실데이터로 확인한 사실

`data/` 의 실제 엑셀 9개(취합파일 + 팀 회신 8개)로 매번 검증한다.

```
요청 109건 → 매칭 69건
요청된 83명 중 편성 60명 · 제외 23명 (전부 「면접관 미매칭」)
팀 요청 탈락 17건 / 16명 · 파싱 경고 7건
학력 학사 45 · 석사 14 · 박사 1 · 합동면접 9명 · 면접관 43명 · 팀 8개
```

| 설정 | 소요일 | 피크 | ① | ② | ③ | ④ |
|---|---|---|---|---|---|---|
| **데모 현행** (8세션 4조) | 3일 | 4조 | **0** | **0** | 6 | 13 |
| DEFAULT_CFG (14세션 4조) | 2일 | 4조 | **0** | **0** | 4 | 5 |
| scheduleAuto (14세션) | 2일 | 3조 | **0** | **0** | 6 | 7 |

- **하드 제약 ①② 는 세 설정 모두 0건.** 엔진은 건강하다
- 3일은 정확하다 — `minDays = ⌈미래혁신팀 17건 ÷ 8세션⌉`. 조를 늘려도 안 줄어든다
- `sched.js` 주석에 *"정원 14, 현행 운영은 8"* 이라 8이 실운영 반영으로 보임

**성능 (요구치 「1초 안에」 대비)**

```
schedule() 전체 편성 60명     0.530 ms
validate() 전체 검증          0.055 ms
scheduleAuto() 후보 11안      6.077 ms
드래그 예고 96칸 증분 판정      0.013 ms   ← 프레임당 여유 충분
```

## 7. 이번 세션에 잡은 결함 — 되풀이 방지

전부 **실브라우저 검증에서만** 드러났다. 단위 테스트로는 안 잡혔다.

| 결함 | 증상 | 원인 |
|---|---|---|
| **무한 렌더 루프** | `Maximum update depth exceeded` | 편집 상태를 위로 올리고 **다시 내려받아** 두 `useEffect` 가 핑퐁. → 아래로는 편성표가 바뀔 때 한 번만, 위로만 보고 |
| **드래그가 드롭 대상을 못 찾음** | `over: null` | dnd-kit 이 칸 위치를 드래그 시작 시점에만 잼. → `MeasuringStrategy.Always` + `closestCenter`. 루프가 있을 땐 강제 재렌더로 **우연히** 동작했다 |
| **미배정 서랍 `display:none`** | 배정 취소가 **조용히 실패** | 요소는 있는데 크기가 0이라 droppable 로 안 잡힘. → 46px 레일로 접되 **사라지지 않게** |
| **Map 키 `String()` 변환** | 복원 후 팀 회신 조인이 조용히 깨짐 | 지원자번호가 숫자면 `1042 ≠ '1042'`. → 원래 타입 보존 |
| **경고 피로** | 첫 타임 13건이 패널 점령 | → `sinceBase` 로 「내가 만든 것」과 가름 |
| **조사 `온타래이(가)`** | AI 스러운 문구 | → `src/lite/hangul.ts` 받침 판별 |
| **`.button:disabled` 스타일 없음** | 못 누르는 버튼이 멀쩡해 보임 | → 회색 + `cursor: not-allowed` |
| **교환 대상 칸만 무채색** | 빈 칸엔 색이 붙는데 점유 칸은 **예고가 통째로 없어** 안전해 보임 | 예고 루프가 점유 칸을 `continue` 로 건너뜀. → §11 |
| **팀이 제자리 제안 가능** | 승인해도 아무 일 없음 | → 팀 화면·큐 양쪽에 가드 |
| **빈 요청함이 백지** | "기능이 적용 안 됐나" 로 읽힘 | → 빈 상태가 스스로 설명 + 팀 화면 지름길 |
| **`vite fs.deny` 무효** | LAN 공개 시 `/data/취합파일.xlsx` 200 | 패턴이 절대경로와 안 맞음. 게다가 기본 목록을 덮어써 **`.git` 이 오히려 열림**. → `**/data/**` 형태 + 기본 목록 함께 명시 |

## 11. 수정 ⑤ — 교환 시 상대 충돌 예고 (완료, 2026-09-02)

### 결함은 3중이었다

| # | 자리 | 증상 |
|---|---|---|
| 1 | `SchedulePage.tsx` 예고 루프 | `if (grid[key] && …) continue` — **점유 칸을 통째로 건너뛰었다.** 빈 칸엔 초록/노랑/빨강이 붙는데 교환 대상 칸만 무채색이라 「문제 없음」으로 읽혔다 |
| 2 | `previewSpot()` | 끌고 있는 사람만 옮겨 계산 — **상대가 밀려갈 자리는 아무도 안 봤다** |
| 3 | 놓은 뒤 토스트 | `placed.filter(끌던 사람 제외)` 로 재서, 교환이면 **상대가 아직 목적지에 앉아 있는 것으로 세어** 곧 사라질 충돌을 알리고 정작 상대가 갈 자리는 빠뜨렸다 |

### 고친 방식 — 먼저 옮기고, 그 위에서 잰다

`previewSpot(…, peer?)` 에 상대를 넘기면 **양쪽을 다 옮긴 배치(`after`)를 먼저 만들고** 그 위에서 각자의 자리를 잰다. 상대를 제자리에 둔 채 재면 결함 3이 그대로 되살아난다.

```ts
readonly peer?: { name: string; clashes: readonly string[]; stray: boolean }
ok = clashes.length === 0 && !peer?.clashes.length      // 한쪽만 깨끗해도 초록이 아니다
```

미배정 카드를 끄는 중이면 상대가 갈 자리가 없다 — 교환이 성립하지 않으므로 `peer` 를 만들지 않는다.

### 화면 — 칸 색 + 커서 옆 라벨 (D16)

| 자리 | 뜻 |
|---|---|
| 칸 빨강 | 양쪽 중 **하나라도** 중복 |
| 칸 노랑 | 학력 구간 밖 (양쪽 중 하나) |
| 칸 초록 | 문제 없음 |
| 커서 옆 라벨 | `도윤아 ⇄ 온나윤` + `온나윤이 갈 자리 — 프로세스개선팀 같은 시간대에 이미 있음` |

**왜 라벨이 필요한가:** 교환은 두 사람이 동시에 움직인다. 밀려나는 상대의 사정은 **화면 반대편 칸**에서 벌어져서, 색만으로는 「누구 때문에 빨간가」를 못 읽는다. 라벨은 `DragOverlay` 안에 있어 커서를 따라다니고, `pointer-events: none` 이라 드롭 대상 판정을 가리지 않는다.

D1(막지 않는다)은 그대로다 — 빨개도 놓인다.

### 검증

- 단위 **181 → 184건**. 새 3건은 실데이터에서 조건에 맞는 짝을 **찾아서** 쓴다(고정 인덱스로 잡으면 데이터가 바뀔 때 조용히 빗나간다)
  - 끄는 쪽은 깨끗한데 상대만 부딪히는 교환 → `peer.clashes` 가 잡고 `ok === false`
  - 곧 비워질 상대 자리 때문에 **없는 중복을 알리지 않는다** (결함 3 회귀 방지)
  - 미배정 카드는 `peer` 가 안 붙는다
- 브라우저 **126 → 134건** (`browser-editor.mjs` 2.5절). `holdOver()` 도우미로 **놓지 않고 붙들어 둔 채** 예고를 재고, 끝나면 원래 칸으로 되돌려 떼서 편성표를 건드리지 않는다
  - 실데이터에서 잡힌 사례: `도윤아 ⇄ 온나윤` → `온나윤이 갈 자리 — 프로세스개선팀 같은 시간대에 이미 있음`
